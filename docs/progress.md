### BUG (upstream): `religious_head` is a title ID, not a character ID

`ck3::Faith::LinkReligiousHead` (`src/ck3_world/religions/faith.cpp:85`) resolves `religious_head`
against the **character** map. In CK3 saves `religious_head` is a **landed title** ID.

Evidence from this save:

- faith 23 has `religious_head=0`; title 0 is `k_papal_state` (the Papacy). Character 0 does not
  exist → `throw std::runtime_error` → converter exits 127.
- faith 67 (`ashari`) has `religious_head=12`; title 12 is `d_sunni`. Character 12 may exist, so
  this silently links the *wrong object* rather than crashing.
- Value distribution in the melt: 108 faiths use `4294967295` (the genuine "no head" sentinel,
  already handled), the rest are small title IDs.

The reference implementation agrees: CK3toEU4 `Faiths::linkReligions` builds
`std::map<ID, TitleKey>` from `titles.getTitles()` and resolves against that, skipping silently
when the ID is absent.

Proposed fix (one PR):

- `religious_head_` → `std::optional<IdPointerPair<Title>>`
- `Faith::LinkReligiousHead(const std::map<long long, std::shared_ptr<Title>>&)`
- `Religions::LinkCharacters(const Characters&)` → `Religions::LinkTitles(const Titles&)`, building
  the id→title map the same way `Characters::LinkTitles` already does
  (`src/ck3_world/characters/characters.cpp:86`)
- Warn-and-skip on a dangling ID instead of throwing (matches CK3toEU4; a destroyed or modded
  head-of-faith title should not abort a conversion)
- Tests to update: `test/ck3_world/religions/religions_tests.cpp` (`LinkingMissingReligiousHead…`
  and the `LinkCharacters` call); `faith_tests.cpp` only covers parsing and is unaffected.

### RESOLVED: the partial world was a mod

`CONVERTER_TEST_Munster_887.ck3` was played with a mod restricting the map to Britannia. That fully
explains the 451 mostly-East-Asian realms, the absent continental European and Middle Eastern
titles, and Wessex appearing as a 15 county duchy. The realm detection was reading the file
correctly the whole time - no bug.

Retiring that save as the primary test case. It stays useful as an edge case (modded, heavily
reduced map). A fresh vanilla 867 day-one save is the new baseline, because the world is then the
known historical setup and the report can be checked against it: Abbasids largest, Francia split
three ways, Byzantium holding Anatolia and the Balkans.

**Implication worth flagging upstream:** the converter has no mod support at all yet, and does not
warn when a save used mods. `CK3World::ParseMeta` has `// TODO(Kmiotek): add mod handling` with the
`mods` keyword commented out, and `LoadLandedTitles` passes `const std::vector<Mod> empty_vector`.
So a modded save is read as though it were vanilla, silently. At minimum the converter should read
the save's `mods` list and warn. This cost a lot of debugging time here and would cost users the
same.

### Fixed: culture/faith fall back to the capital county

The fresh save exposed a real gap: 23 realms reported `culture: unknown` and 21 `faith: unknown`,
including East Francia, Italy and Lotharingia.

Cause: historical rulers frequently carry **no** `culture=` or `faith=` field in the save. Verified
on character 13370 (Louis of Italy) - no culture, no faith. His house (2027, `dynn_Karling`) has
none either, nor does dynasty 2027. CK3toEU4 does not solve this; it reads `culture` off the
character and resets on `4294967295`, nothing more.

Fix (commit `6df8def`): when the holder has neither, read them from the realm capital's entry in
`county_manager`, which CK3 always populates (`c_lombardia` has `culture=133 faith=23`).
Result: **0 unknown culture, 0 unknown faith**. Italy resolves to cisalpine/catholic, East Francia
to franconian/catholic, Lotharingia to french/catholic.

## Session 2026-09-21 (why the mod did nothing, and the fix)

### The mod loaded fine. The file was being rejected.

`debug.log` proved the folder layout was right all along:

    Mounted Data: .../mod/CK3toEU5_Anjou867/main_menu

EU5 mounts a mod's `main_menu` and `in_game` as data roots, exactly like its own DLC
(`dlc/D000_shared/main_menu/...`). So `main_menu/setup/start/10_countries.txt` overrides the vanilla
file, and paths inside resolve as `setup/start/10_countries.txt`.

The real problem was **tag_mappings.txt still carrying EU4 era tags**. EU5 renamed or never had a
number of them - the Ottomans are `TUR`, not `OTT`. 16 tags the converter emitted do not exist in
EU5: ADU AIA AYU BNG DAL EGY GER ITA KOA KRY LOT MLC MSA NPL PRU SIL.

EU5 rejects a block naming an undefined tag, **and a rejected block near the top of the file takes
everything after it with it**. `AIA` (the Abbasids) was second, right after China, so effectively
the whole file was discarded and the vanilla 1337 map showed. **Nothing was logged to error.log** -
this is invisible unless you diff the output against the install.

### EU5 facts established this session

- Version is **1.3.11 "Pavia"** (from the main menu; the install contains no version string at all -
  no launcher-settings.json, and binaries/checksum.txt is just a hash). `data/version.txt` had
  placeholder target bounds of 0.0-2.5, so every generated mod claimed `supported_game_version 2.5.*`.
  Now 1.3.
- EU5 has **no external launcher** for mods. `launcher-v2.sqlite` does not exist for it; it uses
  `playsets.json` and an **in-game mod manager** (`main_menu/gui/mods_gui/mods_gui.gui`), reached
  from the shield icon (`dlc_shield.dds`) in the main menu's right hand icon strip.
- A country definition needs only `color`, `culture_definition`, `religion_definition`, and EU5
  accepts a literal `color = rgb { r g b }` - no named map colour required.
- Country files use tabs between tag and `=` (`NAP\t= {`) and are BOM prefixed. Any validation by
  shell grep will silently undercount; use the parser.

### The fix (commits `e2419d9`, `e77094c`, `28db9fa`)

Rather than hand patching the configurables forever, the converter now reads EU5 and validates
everything it writes:

- `GameDefinitions` scrapes the install: **2339 tags, 2087 cultures, 293 religions**.
- `LocationData` reads EU5's own `06_pops.txt` for the dominant culture and religion of each of its
  **20792 locations**. This is the only source of an EU5 culture available - the configurables map
  culture *groups* by heritage and never cultures, so nothing can turn a CK3 culture into a
  `culture_definition`.
- `CountryDefinitionsFile` writes `in_game/setup/countries/00_converted_countries.txt` for the 16
  undefined tags, colour hashed from the tag so it is stable between runs, culture and religion from
  the capital. Sample: Abbasids -> `levantine_culture`, East Francia -> `rhine_franconian`,
  Italy -> `lombard`, Lotharingia -> `moselle_franconian`.
- A mapped religion EU5 does not define (`religion_map` still says `shiite` for `shia`; `hindu`,
  `coptic`, `zoroastrian`, `protestant` and 23 others are also wrong) falls back to the capital's
  vanilla religion. 3 countries hit this.

Output is back to **234 countries, 8328 locations**, and every tag, culture, religion and location
name in the mod has been checked to exist in EU5.

## Session 2026-09-21 (development and technology)

### Development (commit `b12a936`)

`14_development.txt` is **not** a table of values. Most of it is a formula scoring each location from
terrain, rivers, roads and settlement rank; only the tail lists per location bonuses for notable
places (`astrakhan = 10`). `DevelopmentFile` therefore copies EU5's half verbatim up to its last
closing brace and appends the converted bonuses.

Bonuses are **relative to the save's own median** development, capped at 30 to match EU5's range.
EU5 only bonuses ~294 notable places, so giving all 14000 converted locations an absolute value
would inflate the world globally. 5766 bonuses on the test save, and the scale calibrates itself
whether the save is early or late.

### Technology level

`starting_technology_level` per country in `10_countries.txt`, from **absolute** CK3 development
thresholds (15 / 8 / 3), not median relative. Median relative was self fulfilling: half of any save
sits below its own median by definition, so it would demote half the world no matter when the save
was taken. Absolute thresholds mean an 867 save converts as genuinely backward and a 1337 save as
advanced, which is the point of converting at 1337.

Test save (867): 463 countries at level 0, 488 at 1, 136 at 2, 49 at 3.

## Session 2026-09-21 (cultures)

### The mapping that cannot be written (commit `72f9a23`)

EU5 has **2087 cultures against CK3's 244**, roughly ten times the granularity. There is no
`german` culture in EU5 at all - there are twenty seven regional ones (`westphalian`,
`moselle_franconian`, `swabian`, `upper_palatine`, ...). Only **63** CK3 cultures share a name with
an EU5 one. So a one to one mapping table cannot exist, and flattening Westphalia, Swabia and the
Palatinate into a single "german" would lose far more than it converted.

The approach instead: **EU5's own culture stands wherever CK3 has nothing finer to say.** A location
is only rewritten where the two genuinely disagree - where the EU5 culture belongs to no group the
CK3 heritage maps onto and speaks no language the CK3 culture maps onto. That is the case where a
campaign moved a culture somewhere it does not belong, which is exactly what is worth converting.

Where CK3's culture has no EU5 equivalent - `norse`, and every hybrid or divergent culture a
campaign invents - a definition is **generated** from the configurables so it keeps its CK3 name
rather than being forced into the nearest stranger. A culture definition needs only `language`,
`color` and `culture_groups`, confirmed from EU5's own `00_cultures.info`.

Results on the 867 test save: **3078 locations rewritten, 5591 pop cultures, 58 generated culture
definitions, 9 CK3 cultures unresolved** (no mapped culture group, so EU5's own culture stands).

Only each location's majority culture converts, exactly as religion already does, so EU5's
minorities survive.

### EU5 culture keys are inconsistent about the suffix

`english = { ... }` and `armenian_culture = { ... }` are **both** top level culture keys. Matching
on the bare name alone generated 31 cultures that EU5 already had. Both spellings must be tried.

This is the third time an EU5 file format assumption has cost a wrong answer in this project, all
in the same family: **BOMs and inconsistent keys**. `cat`ting the culture files and stripping the
BOM once hides the first culture of every file, which made `swedish` and `japanese` look absent.
Four cultures (`cunco_culture`, `she_culture`, `manekenk_culture`, `yaros_culture`) are indented by
a space and are invisible to a column anchored grep. The parser found 2087; every shell count in
this session was wrong. **Use the parser.**
